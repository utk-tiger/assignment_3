## G1 and G3: one edge case in each function
*From the implementation (`discovery_agent/tools/licence.py`, `discovery_agent/tools/formats.py`); the outputs quoted are real tool outputs from 2026-11-16.*

- **G1, `extract_licence`: the edge case is a JSON-LD licence that says "Unknown"** (Kaggle fixture: `"license": {"@type": "CreativeWork", "name": "Unknown", "url": ""}`).
  - *What the code does:* evidence is read in order: JSON-LD `license` first, then licence links (creativecommons.org, opendatacommons.org, OGL, choosealicense, SPDX), then licence sentences ("licensed under …"). A name or URL is normalised to a short form (`normalise_licence`, e.g. `…/licenses/by-nc/4.0/legalcode` → `CC BY-NC 4.0`, `…/odbl/1.0/` → `ODbL 1.0`, `choosealicense…/cc0-1.0/` → `CC0 1.0`). It returns None for anything it cannot name exactly: "Creative Commons" or "CC BY" without a version stays None. An explicit "Unknown / unspecified / none / n/a" in JSON-LD is **decisive**. The function stops there and returns `licence_name: None, found_in: "json-ld", snippet: '{"@type": "CreativeWork", "name": "Unknown", "url": ""}'`. It does not go on to read page links, because a site-wide footer link (for example a CC badge for the portal's own content) is not the dataset's licence. By contrast, "Other (specified in description)" is **not** decisive. It points to the page text, so the link and sentence search still runs, and the JSON-LD value is kept only as a fallback.
  - *How it changes the record:* the `licence` field gets `name: null` with the snippet as evidence. So `rule_licence` raises `LIC-UNKNOWN` (a blocker under the register policy: "unknown licence … need Legal review before use") rather than a guessed CC licence. The record shows the publisher was read and said "Unknown", which differs from "no licence found". Real outputs: UCI 321 → `CC BY 4.0`, found_in `link`, snippet "This dataset is licensed under a Creative Commons Attribution 4.0 International (CC BY 4.0) license."; Zenodo → `CC BY 4.0`, found_in `json-ld`; Kaggle → `None`, found_in `json-ld`.
- **G3, `jsonstat_summary`: the edge case is a missing year, which is not a missing cell.** UC1's own Eurostat link (`sdg_11_52`, geo=IT) returns `time` codes 2005, 2007, 2008, …, 2023: **2006 is absent from the time dimension** (EEA produced no PM2.5 maps for 2006). Because the category does not exist, `size` is 18 years × 2 units = 36 expected cells and all 36 have values. So `MISSING_CELLS` cannot see the gap.
  - *What the code does:* it counts missing cells properly. A `null` in a dense `value` list, or an index absent or null in a sparse `value` dict, counts as missing, never as zero (contract test: `value: [1.0, None, 2.0, 3.0]` → value_count 3, missing_cells 1, `MISSING_CELLS`). Indexes may be lists or `{code: position}` dicts (ordered by position, so `{"2011": 1, "2010": 0}` → 2010, 2011). `status` may be a dict, a list or a single string. It also adds one warning beyond the contract, **`TIME_GAPS`**, when plain year codes skip a year. Geo codes are checked against the real ISO 3166-1 alpha-2 list, so Eurostat's `UK` and `EL` and aggregates such as `EU27_2020` raise `NON_ISO_GEO_CODES`.
  - *How it changes the summary:* the live summary is `time: {first: "2005", last: "2023"}`, `expected_cells: 36`, `value_count: 36`, `missing_cells: 0`, `warnings: ["TIME_GAPS"]`. Without `TIME_GAPS`, a profiler reading "first 2005, last 2023, 0 missing" would assume a complete annual series. With it, the record can say N6 has no 2006 value, and that the prototype window (2004-03-10..2005-04-04) only overlaps 2005, the first year.

## G5: Verdict calibration

- **What changed in `discovery_agent/prompts/risk_assessor.md`:** the G5 comment was replaced by a `## Verdict calibration` section with 12 ordered rules (first match wins). Each maps flag patterns, severity (`config/red_flags.json`) and the source's role (must = core, should/could = context) to a verdict. The rules name no UC1 or UC2 source, so they carry over to a new use case. The reasoning behind each:
  1. *Unresolvable blockers* (refused host, expired agreement, out of every window, consent gap, policy ban) → `not_feasible`. No condition anyone on the project owns can clear them, and guardrail refusals are findings, never dismissed.
  2. *Resolvable blockers* (`LIC-UNKNOWN` with an official terms page; non-commercial or research-only licence used only for prototype or benchmark in a public-sector project) → `feasible_with_conditions` with Legal as owner. This follows the register policy's "need Legal review before use", which is a condition, not a ban. Production use of a non-commercial licence stays `not_feasible`.
  3. *Grain coarser than a core need* → `not_feasible` for that need, because coarse data cannot be disaggregated. For context needs (`could`/`should`), coarse or national data is acceptable with the limitation stated.
  4. *Per-window judgement*: covering at least one target window fully → `feasible_with_conditions`, with the missed window named. This keeps a source that is good for one window from being thrown away because of the other.
  5. *Stale is fine for a historical window*: `FRS-STALE` is dismissed with a reason when the target window itself ends before the cut-off (a 2004–05 prototype window can only be served by 2004–05 data). It is kept when the source is meant to serve a current window.
  6. *Fixable data-quality and documentation issues* (catalog-vs-wiki conflict, definition change at a known date, sentinels, metadata contradiction, DST, restricted with a request process, known migration gap) → `feasible_with_conditions` with one concrete fix each. They change how the data is used, not whether it can be used.
  7. *No join path for a core need* (the documentation says no mapping exists) → that need is `unmet` and its source `not_feasible`. A must-need that cannot be joined makes the overall verdict `not_feasible`.
  8. *Majors only* → `feasible_with_conditions` when each has an achievable condition with an owner.
  9. *Minors only* → `feasible`; attribution and staged download are recorded as notes.
  10. *Duplicates and geography*: the weaker copy is flagged and named. A different geography gives `not_feasible` when the source must describe the client's site, and `feasible_with_conditions` when it is a benchmark or context.
  11. *Dismissal discipline*: dismissing a rule flag requires naming the field and value. Guardrail, agreement, consent and PII flags are never dismissed.
  12. *Consistency check*: no blocker on a `feasible` source, every conditional verdict lists a condition, every `not_feasible` names its deciding rule.
